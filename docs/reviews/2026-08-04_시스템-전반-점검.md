### 1. [sql/deploy/CJAirPort_install.sql](sql/deploy/CJAirPort_install.sql) 보조 인덱스가 사실상 없다 — 운영 규모에서 가장 먼저 터진다

DB 전수 확인 결과 인덱스는 **PK(클러스터드) 22개 + `UX_tb_card_value` 1개가 전부**다. 검색·필터·정렬에 쓰는 컬럼에 보조 인덱스가 하나도 없다.

가장 급한 것은 **`tb_system_log`** 다. 감사 대상이 "메뉴 접속·조회·입력·수정·삭제" 전부라 가장 빨리 커지는데, PK 는 `log_id` 하나뿐이라 감사추적 화면의 `WHERE reg_dt >= ? ... ORDER BY reg_dt DESC` 는 **탐색(seek)이 불가능해 전건 스캔 + 정렬**로만 처리된다.

현재 개발 DB 실측: **하루 평균 464건**(26일간 12,084건, 최근 7일 2,332건). 현장에서 다수 사용자가 쓰면 이보다 훨씬 커지므로 1년이면 수십만~수백만 건이고, 화면은 갈수록 느려진다.

→ 최소 아래 정도는 설치 스크립트에 넣는 것이 좋다.

```sql
CREATE INDEX IX_tb_system_log_reg_dt ON dbo.tb_system_log (reg_dt DESC) INCLUDE (log_id, user_id, action_type, menu_id);
CREATE INDEX IX_tb_card_person      ON dbo.tb_card (person_id) WHERE del_yn = 'N';
CREATE INDEX IX_tb_card_car         ON dbo.tb_card (car_id)    WHERE del_yn = 'N';
CREATE INDEX IX_tb_person_type      ON dbo.tb_person (del_yn, person_type, company_code);
CREATE INDEX IX_tb_visit_search     ON dbo.tb_visit (del_yn, visit_type, work_start_dt);
```

`tb_card(person_id)` 가 특히 중요하다 — 정규인원 목록은 **행마다** 카드 장수 상관 서브쿼리를 돌리고(`listColumns` 서브쿼리 2개), 카드번호 검색도 `EXISTS (… WHERE cd.person_id = …)` 를 쓰는데 지금은 매번 `tb_card` 전체를 훑는다. 방문 목록도 행마다 방문객·차량 COUNT 서브쿼리 2개를 돈다(다만 `tb_visit_person`/`tb_visit_car` 는 PK 선두가 `visit_no` 라 이쪽은 탐색이 된다).

### 3. [LoginService.java:21](src/main/java/AirPort/service/LoginService.java:21) 계정 잠금이 문서에는 있고 코드에는 없다 — 무제한 비밀번호 시도가 가능하다

덧붙여 `updateLoginFailCnt` 와 `TbCarAcGroupMapper.selectCodeNames` 는 현재 **호출처가 없는 죽은 코드**다(전체에서 이 2개뿐 — 전반적인 코드 위생은 좋다).

### 4. [KioskVisitService.java:69](src/main/java/AirPort/service/KioskVisitService.java:69) 무인증 신청에 건수·개수 제한이 없다

`/kiosk/**` 는 인증·메뉴통제 제외 경로다. `create()` 는 필수값은 꼼꼼히 검증하지만 **방문객·차량 개수 상한도, 요청 빈도 제한도 없다**. 신청 1건마다 `tb_person` 행이 생기고 인원ID 가 채번되므로, 스크립트로 반복 호출하면 인원 테이블과 방문 테이블이 무한정 불어난다(관리자 목록도 같이 오염된다).

→ 방문객·차량 개수 상한(예: 각 50), 그리고 IP·시간당 신청 건수 제한을 두는 편이 좋다. 키오스크는 물리적으로 통제된 단말이라는 전제가 있지만, 같은 내부망의 아무 PC 나 이 엔드포인트를 부를 수 있다.

### 5. [VisitService.java:117](src/main/java/AirPort/service/VisitService.java:117) 인솔자 검색이 전건을 읽어 전건 복호화한다 (무인증 경로 포함)

`searchManagersPublic` 은 `personMapper.selectRegular()` 로 **정규인원 전체**를 읽어 한 명씩 ARIA 복호화한 뒤 Java 에서 필터한다. 성명이 결정적 암호문이라 SQL 로 검색할 수 없는 구조적 제약 때문이고, "빈 검색어=결과 없음 / 성명은 완전일치 / 최대 50건"으로 명단 훑기를 막아 둔 것도 확인했다 — 설계 의도는 명확하다.

다만 두 가지가 남는다.

- **비용**: 무인증 엔드포인트에서 정규인원 수에 비례해 전체 조회 + N회 복호화가 매 요청 일어난다. 수천 명 규모면 요청 하나가 무거워지고, 반복 호출로 CPU 를 소모시킬 수 있다.
- **훑기 방지의 구멍**: 성명은 완전일치지만 **인원ID 는 부분일치**(`personId.contains(kw)`)다. 인원ID 가 `400001` 처럼 연속 번호라 `"4000"` 만 넣어도 최대 50명의 **복호화된 성명**이 무인증으로 돌아온다.

→ 인원ID 도 완전일치(또는 최소 길이 제한)로 좁히면 의도한 방어가 완성된다.

### 6. [PersonService.java](src/main/java/AirPort/service/PersonService.java) 트랜잭션이 BiostarX 응답을 기다리는 동안 DB 커넥션을 잡고 있다

"BiostarX 동기화 실패면 저장 취소(롤백)"는 이 시스템의 핵심 정합성 정책이고 그 자체는 옳다. 다만 그 결과로 **외부 HTTP 왕복이 트랜잭션 안에 들어간다**. 인원 저장 1건은 사용자 upsert·사진 업로드·카드 등록 등 여러 번 왕복할 수 있다.

타임아웃은 잡혀 있다(연결 5초 / 요청 7~10초, [BiostarSession.java:107](src/main/java/AirPort/adapter/BiostarSession.java:107)). 문제는 **커넥션 풀 설정이 없어 HikariCP 기본값 10** 이라는 점이다. BiostarX 가 느려지면 등록 작업 10건만으로 풀이 마르고 **조회를 포함한 시스템 전체가 멈춘다**.

→ 롤백 정책은 유지하되, `spring.datasource.hikari.maximum-pool-size` 를 현장 동시 사용자 수에 맞춰 명시하고(예: 20~30) `deploy/application.properties.example` 에도 넣는 것이 좋다. `docs/deployment.md` 에 풀·타임아웃 언급이 전혀 없다.

### 7. BiostarX 불일치를 되돌릴 수단이 없다

`resync`/재동기화/일괄 대사 기능이 코드 전체에 **없다**(확인). 지금 구조는 실패 시 롤백해서 불일치를 *만들지 않는* 데 집중하는데, 이 방식은 다음을 못 다룬다.

- 롤백 자체가 실패한 경우(트랜잭션은 되돌아갔는데 BiostarX 쪽 쓰기는 이미 반영된 경우)
- BiostarX 를 관리자 콘솔에서 직접 수정한 경우
- 이전 버전 버그로 이미 어긋나 있는 데이터 (이번 세션에서만 얼굴 템플릿·카드 잔존 등으로 실제 발생했다)

→ 최소한 **대사(비교) 화면 하나** — 시스템 vs BiostarX 사용자·카드 목록 차이를 보여주는 조회 기능 — 이 있으면 현장에서 원인 추적이 훨씬 쉬워진다. 자동 복구까지 갈 필요는 없다.

## 참고 — 확인만 하고 넘긴 것

- **비밀번호를 ARIA 대칭 암호로 저장**한다([LoginService.java:26](src/main/java/AirPort/service/LoginService.java:26)). 일반적인 보안 기준으로는 단방향 해시(bcrypt 등)가 맞다 — 지금은 키가 유출되면 전 계정 비밀번호가 복원되고, 결정적(ECB)이라 같은 비밀번호를 쓰는 계정끼리 암호문이 같아 DB 만 봐도 드러난다. 다만 이는 AGENTS §4 불변식이 명시한 프로젝트 규칙(발주 요구사항으로 보인다)이라 임의로 바꿀 사안이 아니다. **발주처와 확인이 필요한 항목**으로 남긴다.
- 얼굴 사진은 4MB(디코드 후) 제한인데 JSON 본문으로 오므로 multipart 5MB 제한이 적용되지 않는다. base64 로 실려 요청 하나가 5~7MB 가 될 수 있다. 현재 규모에서 문제는 없다.
- `tb_person_photo` 는 4건에 4.5MB(건당 약 1.1MB, BASE64 라 원본보다 33% 큼). 정규인원이 수천 명이면 수 GB 가 DB 에 쌓인다. 백업 일원화를 위한 의도적 설계이나 **용량 산정은 해 두는 편이 좋다**.
- 카드번호(`biostar_card_value`)는 `nvarchar` 라 정렬이 문자열 순이다(`111` → `11111111` → `111222`). 자리수가 제각각인 식별자라 틀렸다고 단정하긴 어려워 그대로 두었다.
- 하위 서비스(`VisitRosterService`·`CardService.saveCards` 등)에 `@Transactional` 이 없는 것은 **호출자의 트랜잭션에 참여시키려는 의도**이며 javadoc 에 명시돼 있다. 결함이 아니다.
- 서비스 26개 중 12개에 직접 대응하는 테스트가 없다(`AccountService`·`CarService`·`CompanyService`·`LoginService`·`LoginUserService`·`SystemLogService` 등). 대부분 단순 CRUD 라 우선순위는 낮지만, **`LoginService`(인증)와 `KioskVisitService`(무인증 입력)** 는 테스트 가치가 높다.
