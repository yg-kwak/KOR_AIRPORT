- [CardService.java:174](../../src/main/java/AirPort/service/CardService.java:174) `register()` 가 `known.getPersonId() != null` 만 거부 → 차량 카드를 그대로 재사용해 준다.
- [TbCardMapper.xml:64](../../src/main/resources/mapper/TbCardMapper.xml:64) 인원 흐름의 `update` 가 `person_id` 만 세팅하고 `car_id` 를 비우지 않는다 → 두 컬럼이 동시에 채워진다.

반대 방향인 [CompanyCarService.java:194](../../src/main/java/AirPort/service/CompanyCarService.java:194) `issueCard()` 는 `personId`·`carId` 를 **둘 다** 검사해 막는다. 즉 한쪽만 뚫려 있는 비대칭이다.

출입통제 시스템에서 한 장의 카드가 사람과 차량에 동시에 귀속되면 출입 이력의 주체가 모호해진다.

**수정 방향**: ① `selectUnassigned` 에 `AND car_id IS NULL` 추가 ② `register()` 에서 `carId != null` 도 거부 ③ 인원 흐름 `update` 에 `car_id = NULL` 추가(인원 카드로 전환됨을 명시). 나아가 스키마에 배타성 제약(`CHECK (person_id IS NULL OR car_id IS NULL)`)을 두면 코드 실수와 무관하게 강제된다.

**수정 방향**: 삭제 차단 조건과 할당여부 판정을 `person_id IS NOT NULL OR car_id IS NOT NULL` 로 통일.

POST 성공 *후* `updateBiostarCardId`나 **commit 자체가 실패**하면(교착·커넥션 절단) 장비엔 카드가 남고 DB는 롤백돼 여전히 고아가 된다. 다만 이번 변경으로 *가장 흔한 실패*(unique/CHECK 제약)는 POST 이전으로 옮겨졌고 동시요청 경합도 insert-선행으로 막혀, 잔여 위험은 "성공한 POST 뒤의 드문 실패"로 줄었다. 근본 해소(커밋 후 동기화/보상)는 별건으로 남긴다 — 커밋 메시지에도 "사실상 없음"으로 정직하게 표기됨.
- **`registerBiostar` 의 호출 계약이 코드로 강제되지 않는다** — `@Transactional` 없는 package-private 메서드로, "활성 트랜잭션 + insert 선행" 상태에서만 안전하다(Javadoc 에 명시). 지금 두 호출자([CardService.createCard:80](../../src/main/java/AirPort/service/CardService.java:80)·[CompanyCarService.issueCard:221](../../src/main/java/AirPort/service/CompanyCarService.java:221))는 지키지만, 트랜잭션 없이 부르면 POST 실패가 앞선 insert 를 롤백하지 못한다. 단위 테스트(어댑터 목)로 이 순서·롤백을 고정하는 게 이상적(기존 🟡 '테스트 부재'와 같은 맥락).
  - **조치(2026-07-23)**: `registerBiostar` 첫머리에 가드 2개 추가 — ① `TransactionSynchronizationManager.isActualTransactionActive()` 로 활성 트랜잭션 강제(스레드 바인딩이라 self-invocation 에도 정확) ② `row.getCardId()==null` 이면 insert 선행 위반으로 예외. 계약 위반은 즉시 `IllegalStateException` 으로 막는다.
