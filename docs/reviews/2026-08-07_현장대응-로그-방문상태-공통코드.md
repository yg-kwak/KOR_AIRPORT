## 🔴 차단

### 🔴-1 요청 로그에 개인정보(성명 검색어)가 평문으로 남는다
[MdcFilter.java:59](src/main/java/AirPort/config/MdcFilter.java:59) — 도입 커밋 `5d97eb1`

요청 로그가 **쿼리스트링을 그대로** 기록한다. 목록 검색어(`keyword`)에 성명을 넣으면
그 이름이 `cjairport.{날짜}.0.txt` 에 평문으로 남는다.

```
REQUEST - GET /person/person/list?page=1&size=30&keyword=홍길동&searchType=personName 200 141ms
REQUEST - GET /kiosk/visit/managers?keyword=4              ← 현장 로그에서 실제 확인
```

`tb_person.person_name` 은 ARIA 로 암호화 저장하는데(security.md) 같은 값이 로그에는 평문으로
쌓인다. 로그 파일은 60일 보관이고, 키오스크 경로(`/kiosk/**`)는 **무인증**이라 방문객이 입력한
인솔자 성명까지 남는다.

→ 수정 방향: 요청 로그에서 쿼리스트링을 통째로 남기지 말고 **허용 목록(page·size·sort·dir 등)만**
남기거나, `keyword`·`personId` 등 값이 있는 파라미터는 `keyword=***` 로 마스킹한다.
업무 이력(AUDIT)은 이미 "결과 N건"만 남기고 있어 손댈 필요 없다.

### 🔴-2 삭제한 인원ID 를 재사용하면 이전 인원의 얼굴 사진이 남는다
[PersonService.java:281](src/main/java/AirPort/service/PersonService.java:281) — 도입 커밋 `17be18d`

`savePhoto` 는 **사진이 있을 때만** upsert 한다. 삭제(`deleteOne`)는 `tb_person_photo` 를 지우지
않는다. 그래서 `revive` 로 같은 번호를 재사용하면서 얼굴을 새로 넣지 않으면 **이전 인원의 사진이
그대로 붙는다** — 수정 모달·카드 출력에 다른 사람 얼굴이 나온다.

`update()` 에는 사진이 없으면 지우는 분기가 있는데(`photoMapper.deleteByPerson`), 등록 경로에는
없다. 첨부문서(`tb_person_file`)는 파일명이 비면 지우므로 같은 문제가 없다.

→ 수정 방향: `create()` 의 revive 분기에서 `photoMapper.deleteByPerson(personId)` 를 먼저 부르거나,
`deleteOne()` 에서 사진을 함께 지운다(삭제 시 정리가 더 안전 — 소프트 삭제 상태에서도 생체정보를
남길 이유가 없다).

### 🔴-3 현장 서버 IP 가 문서에 커밋됐다
[integration.md:52](../integration.md) — 도입 커밋 `29d36a6`

```
10.81.10.111:9443     ->  https://10.81.10.111:9443
```

§4 의 "비밀값 금지" 는 자격증명 중심이지만, **현장 BiostarX/서버 IP 는 커밋하지 않는다**는 것이
이 저장소의 운영 전제다(`init.txt` 도 `<서버IP>` 자리표시자를 쓴다). 접속정보 노출 면에서
포트까지 함께 적혀 있어 더 구체적이다.

→ 수정 방향: `<서버IP>:9443` 자리표시자로 바꾼다. 설명에 필요한 건 형식이지 실제 주소가 아니다.

## 🟡 권고

### 🟡-1 호스트명 검증 해제가 JVM 전역이다
[BiostarSession.java:100](src/main/java/AirPort/adapter/BiostarSession.java:100)

`jdk.internal.httpclient.disableHostnameVerification=true` 는 프로세스 전체의 `HttpClient` 에
적용된다. 지금은 BiostarX 연동이 유일한 사용처라 실질 영향이 없고 코드에 이유도 적혀 있지만,
나중에 다른 HTTPS 연동이 생기면 **아무도 모르게 검증이 꺼진 채** 나간다.

→ `HttpClient` 를 새로 만드는 코드가 추가되면 이 전제를 확인하도록 code-lint 규칙을 하나 두거나,
BiostarX 인증서를 서버 IP SAN 으로 재발급해 이 속성을 걷어내는 것이 근본 해법이다.

### 🟡-2 파생 상태(VS05)는 테이블을 직접 조회하면 보이지 않는다
[TbVisitMapper.xml:10](src/main/resources/mapper/TbVisitMapper.xml:10)

`tb_visit.status_code` 에는 VS03 만 저장되고 미반납은 조회 시 계산한다(의도된 설계, database.md 반영).
다만 발주처 리포트나 직접 SQL 은 미반납을 볼 수 없다.

→ 외부에서 조회할 계획이 있으면 같은 식을 담은 뷰(`vw_visit`)를 하나 제공한다.

### 🟡-3 순찰·대여 인원ID 접두(PL/RT)가 미확정이다

## 🟢 양호

- **MyBatis 규약 준수** — 이번 변경의 SQL 은 전부 mapper XML, 파라미터는 `#{}`, Java 내 인라인 SQL·
  문자열 연결 SQL 0건, `@Entity`/JpaRepository 0건.
- **외부 연동 격리 유지** — service 계층에서 `HttpClient`/`RestTemplate` 직접 호출 0건. BiostarX 는
  전부 `adapter` 경유.
- **감사 누락 없음** — 새로 생긴 상태 전이(방문 자동 마감, 계정 잠금 해제, 카드 발급 차단)가 모두
  `tb_system_log` 에 기록된다. 실패 경로는 `logAlways`(REQUIRES_NEW)로 롤백돼도 남는다.
- **회귀를 규칙으로 막았다** — 정렬 헤더↔mapper 대조[6], MSSQL 2016 미지원 함수 차단[7]을 lint 에
  추가하고 되돌려서 실제로 잡히는 것까지 확인했다.
- **테스트 94건 통과** — 신규 로직마다 추가(카드 발급 제한 · 계정 잠금 · 인원ID 재사용 · 카드 미발급
  방문 · 미반납 전이 · 출입종료일 상한).
- **상한이 한 곳으로 모였다** — 출입종료일이 Java·JS 두 곳에 하드코딩돼 있던 것을 설정 하나로
  통일하고 화면까지 내려, 검증 기준이 어긋날 여지를 없앴다.
