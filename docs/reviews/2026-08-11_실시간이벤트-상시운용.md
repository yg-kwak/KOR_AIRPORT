# 실시간 이벤트 — 여러 클라이언트 상시 운용 검토

- **검토 대상**: 미커밋 작업분 (모니터링 → 실시간 이벤트, `MonitorService`·`BiostarEventSocket`·`event.js`)
- **검토자**: sjpark2 / 2026-08-11
- **전제**: 여러 대의 클라이언트가 이 화면을 **하루 종일 켜 둔다**(상황실 모니터 용도)
- **결과 요약**: 🔴 5 / 🟡 6 / 🟢 4

가장 위험한 것은 죽는 것이 아니라 **죽은 줄 모르는 것**이다. 아래 🔴 중 4건이 화면에는
"수신 중"으로 보이면서 이벤트만 안 오는 형태로 끝난다.

---

## 🔴 차단 — 상시 운용 전 반드시 고칠 것

### 🔴-1 오류가 화면에 도달하지 않는다 (모든 실패가 "수신 중"으로 보인다)

`MonitorService.statusPayload` 는 `connected` 를 `eventSocket.isConnected()`(소켓 객체가 있는가)로
계산하는데, 소켓은 열려 있고 **세션 인증이나 events/start 만 실패**한 경우가 정확히 그 상태다.

```java
private Map<String, Object> statusPayload(String error) {
  return Map.of("connected", eventSocket.isConnected(), "message", error == null ? "" : error);
}
```

화면은 `connected` 가 참이면 메시지를 버린다:

```js
if (s.connected) { el.textContent = '수신 중'; }   // ← 오류 문구가 사라진다
else { el.textContent = s.message; }
```

→ 소켓이 세션을 거부해도, events/start 가 실패해도 화면은 **"수신 중"**. 아무도 이상을 모른다.
**수정 방향**: `connected` 를 "이벤트를 받을 수 있는 상태"로 정의한다(소켓 존재 + 세션 확인됨 +
events/start 성공). 오류가 있으면 무조건 오류를 표시한다.

### 🔴-2 events/start 실패 시 재시도가 없다 — 영구 정지

```java
String err = eventAdapter.start(ip, loginId, password);
if (err != null) {
  fail("실시간 이벤트를 시작하지 못했습니다: " + err);
  return;                     // ← scheduleRetry() 가 없다
}
```

소켓은 열린 채로 남고 `wanted` 도 참이라 `dropAndRetry` 도 안 걸린다. 장비가 잠깐 바빠서 한 번
실패하면 **그 뒤로 영원히 이벤트가 오지 않는다**(🔴-1 때문에 화면은 "수신 중").
소켓 세션 거부(`checkAuthReply` → `fail`)도 같은 경로다.

**수정 방향**: 두 경우 모두 소켓을 버리고 `scheduleRetry()`.

### 🔴-3 구독자 교대 시 소켓이 죽는 경합

`MonitorService.release`(마지막 구독자 이탈 → `stop()`)와 `subscribe`(→ `start()`)가 겹칠 수 있다.

```
A 스레드: viewers.remove(A) → 비었다고 판단 ────────────┐
B 스레드:            viewers.put(B) → start() → wanted 아직 true → 즉시 return
A 스레드:                                        └→ stop() → wanted=false, 소켓 abort
```

B 는 구독자 목록에 있는데 소켓은 닫혔고 아무도 다시 열지 않는다. **B 의 화면은 새로고침 전까지
영구 정지.** 여러 사람이 화면을 여닫는 상시 운용에서 실제로 밟힌다.

**수정 방향**: 소켓 수명 결정을 한 잠금 안에서 한다(구독자 수 확인과 start/stop 을 원자적으로).

### 🔴-4 우리 웹 세션이 1시간에 만료된다 — 화면이 조용히 죽는다

`application.properties`: `server.servlet.session.timeout=1h`

SSE 는 **요청 하나**다. 연결이 유지되는 동안 세션의 최종접근시각은 갱신되지 않는다(Tomcat 기본
`ACTIVITY_CHECK=false`). 25초 ping 은 서버→클라이언트라 요청이 아니다.

→ 1시간 뒤 세션 만료. 그때 흐르던 SSE 는 계속 살아 있지만, **네트워크가 한 번만 끊겨도**
EventSource 가 자동 재연결하면서 `/monitor/event/stream` 이 로그인 페이지로 리다이렉트되고,
`text/event-stream` 이 아니므로 EventSource 는 오류 → 3초마다 재시도를 **영원히** 반복한다.
화면에는 "연결 재시도 중"만 남는다. 사용자가 상황실에 없으면 몇 시간을 그렇게 있는다.

**수정 방향(택1)**: ① 화면이 주기적으로(예 10분) 가벼운 인증 요청을 보내 세션을 살린다.
② 이 화면 전용으로 세션 만료를 늘린다. ③ 스트림이 401 이면 화면이 로그인으로 안내한다.
**②만으로는 부족하다** — 어차피 언젠가는 만료되므로 ③은 같이 필요하다.

### 🔴-5 BiostarX 세션 idle 만료 — 1시간 이상 켜 둘 때의 본체

소켓은 연결 시점의 `bs-session-id` 에 묶인다. 그 뒤로 우리는 **그 세션을 쓰는 요청을 전혀 보내지
않는다**(인증이 없으면 `authImage` 도 안 부른다). BiostarX 세션에 idle 만료가 있으면 새벽처럼
통행이 없는 시간대에 세션이 죽고, 그 뒤 출근 시간에 **이벤트가 안 온다**.

장비가 그때 소켓을 닫아 주면 🔴-2 를 고친 재연결로 복구되지만, **닫아 주지 않으면 복구 경로가
없다**. 어느 쪽인지는 확인하지 못했다(검증하려면 idle 상태로 수 시간 관찰이 필요).

또 하나: `BiostarSession` 은 세션을 **하나만 캐시**한다. 다른 화면(정규인원 저장, 카드 발급 등)에서
401 이 나면 `refresh()` 가 **새로 로그인**한다. 그 순간 소켓이 묶인 세션이 무효화될 수 있다.

**수정 방향**: 감시견(watchdog)을 둔다 — 몇 분마다 값싼 인증 요청 한 번(세션 idle 갱신 + 죽음 탐지).
실패하면 소켓을 버리고 재연결. "이벤트가 안 오는 것"과 "지금 아무도 안 지나가는 것"은 구분할 수
없으므로, 무이벤트만으로 판단하면 안 되고 **능동 확인**이어야 한다.

## 🟡 권고

### 🟡-1 ping 이 전체 스케줄러를 막을 수 있다 (정기 파기까지 멈춘다)

Spring Boot 기본 스케줄러 풀은 **스레드 1개**다(`spring.task.scheduling.pool.size` 미설정).
`MonitorService.ping()`(25초)과 `VisitPurgeService`(매일 03:00)가 **같은 한 스레드**를 쓴다.
느린 클라이언트로 SSE 쓰기가 지연되면 ping 이 물리고, 그 시간에 파기 배치가 못 돈다.
→ 풀 크기를 2 이상으로 올리거나 ping 을 전용 스레드로 뺀다.

### 🟡-2 재연결 폭주가 감사추적을 채운다

`subscribe()` 는 구독 시작마다 감사 1줄을 남긴다. EventSource 는 실패 시 **3초마다** 재시도한다
(🔴-4 상황). 클라이언트 5대면 분당 100줄. 감사추적이 이 로그로 덮인다.
→ 같은 사용자·같은 단말기의 재연결은 일정 시간 내 1회만 기록하거나, 최초 구독만 기록한다.

### 🟡-3 보강 대기열에 상한이 없다

`worker` 는 무제한 큐의 단일 스레드다. `authImage` 는 최대 10초 대기한다(장비 지연 시).
출근 시간대에 인증이 몰리면 큐가 밀려 **몇 분 전 사람이 화면에 뜬다**. 실시간 화면에서 이건
틀린 정보다. → 큐 상한을 두고 넘치면 오래된 것을 버린다(최신이 중요한 화면이다).

### 🟡-4 브라우저 동시 연결 한도 (같은 PC 에서 여러 탭)

HTTP/2 가 꺼져 있어(`server.http2.enabled` 미설정) HTTP/1.1 이다. 브라우저는 **오리진당 6 연결**이
한도이고 SSE 는 그중 하나를 영구 점유한다. 한 PC 에서 이 화면을 6개 탭 열면 그 오리진의 다른
요청이 모두 멈춘다. → `server.http2.enabled=true` 를 켜면 사라진다.

### 🟡-5 역방향 프록시를 두면 SSE 가 버퍼링될 수 있다

nginx 등을 앞에 두면 응답을 버퍼링해 이벤트가 뭉쳐서 도착하거나 안 온다.
→ 배포에 프록시가 낀다면 해당 경로에 버퍼링 해제(`X-Accel-Buffering: no` 또는 `proxy_buffering off`).

### 🟡-6 사진 때문에 클라이언트 수만큼 트래픽이 곱해진다

인증 1건의 payload 는 사진 2장 포함 **약 25KB**. 보강은 한 번이지만 전송은 구독자 수만큼이다.
클라이언트 10대 × 분당 30건이면 약 7.5MB/분. 내부망이면 문제없지만, 클라이언트가 더 늘거나
회선이 느리면 느린 클라이언트가 ping 을 물고(🟡-1) 연쇄한다.
→ 지난 인증 6칸은 축소 이미지로 보내는 것을 고려.

## 🟢 양호

- **소켓은 하나만 연다** — 구독자가 몇 명이든 장비 연결은 1개(`wanted` 플래그). 질문 1(부하)에
  대해서는 설계가 맞다. 클라이언트 10대여도 BiostarX 입장에서는 연결 1개다.
- **마지막 구독자가 떠나면 소켓을 닫는다** — 아무도 안 보는 이벤트를 계속 받지 않는다.
- **끊김 감지 + 재연결** — `onClose`/`onError` → 10초 뒤 재연결, 재연결마다 세션 재발급.
  질문 3(자동 복구)은 **소켓이 닫히는 형태의 장애에 한해** 동작한다(🔴-2·🔴-5 참고).
- **SSE 전송을 emitter 마다 잠근다** — 이벤트 스레드와 ping 스레드가 겹쳐 프레임이 깨지는 것을 막는다.
- **보강을 소켓 스레드에서 분리** — 수신이 DB·HTTP 때문에 막히지 않는다. 단일 스레드라 순서도 지켜진다.

# 재검토 — 지적 전량 반영 (2026-08-11)

🔴 5건 + 🟡 6건 중 6건을 고쳤다. 남긴 것은 배포 환경에 달린 2건뿐이다.

## 🔴 반영

| 항목 | 어떻게 고쳤나 |
|---|---|
| 🔴-1 오류가 화면에 안 감 | `isConnected()`(소켓 객체 유무) → **`isReady()`**(소켓+세션+events/start 전부 성공). 소켓이 마지막 실패 사유(`error()`)를 들고 있고, 화면은 **사유가 있으면 사유를 먼저** 보여 준다. |
| 🔴-2 재시도 없는 영구 정지 | 로그인·핸드셰이크·세션거부·events/start — **모든 실패가 `dropAndRetry` 한 곳으로 모인다.** 소켓을 버리고 사유를 남기고 10초 뒤 재연결. 소켓만 열린 채 남는 상태가 사라졌다. |
| 🔴-3 구독자 교대 경합 | 구독자 목록 변경과 소켓 start/stop 을 **한 잠금(`viewerLock`)** 안에서 한다. 소켓 연결을 비동기로 돌려 이 잠금은 짧게 유지된다(구독 응답도 빨라졌다). |
| 🔴-4 웹 세션 1시간 만료 | 화면이 5분마다 `/monitor/event/alive` 를 호출해 세션을 갱신한다. 이미 끊겼으면 401 → 기존 api 래퍼가 로그인 화면으로 보낸다. **좀비 상태로 남지 않는다.** |
| 🔴-5 BiostarX 세션 idle 만료 | 3분마다 `verify()` — `events/start` 재호출로 **살아있음을 능동 확인**하고 세션 idle 시간도 함께 갱신한다. 성공했더라도 **세션 ID 가 바뀌었으면**(다른 화면이 재로그인시킨 경우) 죽은 세션에 묶인 것이므로 재연결한다. |

## 🟡 반영

- **🟡-1** `spring.task.scheduling.pool.size=4` — ping 이 정기 파기를 막지 못한다.
- **🟡-2** 같은 사용자·단말기 구독 감사는 **10분에 한 번**만. 재연결 폭주가 감사추적을 덮지 않는다.
- **🟡-3** 보강 대기열 상한 50 + `DiscardOldestPolicy` — 밀리면 오래된 것을 버린다(실시간 화면은 최신이 중요하다).
- **🟡-4** `server.http2.enabled=true` — 한 PC 에서 여러 탭을 열어도 연결 한도에 걸리지 않는다.

## 남긴 것

- **🟡-5 프록시 버퍼링** — 배포 구성에 프록시가 없어 지금은 해당 없음. 앞단에 nginx 등을 두면 `/monitor/event/stream` 에 버퍼링 해제가 필요하다.
- **🟡-6 사진 트래픽** — 내부망 + 현재 클라이언트 수에서는 문제되지 않는다. 대수가 크게 늘면 지난 인증 6칸을 축소 이미지로 보내는 것을 검토.

## 확인한 것 (개발 서버 + 실제 장비)

- 클라이언트 **3대 동시 구독 → BiostarX 소켓은 1개**(로그에 연결 1줄), 감사도 **1줄**(예전 같으면 3줄).
- A·B 이탈 후 **C 는 계속 수신** — 교대 경합이 나던 구간.
- 전원 이탈 25초 뒤 소켓 자동 종료.
- `/monitor/event/alive` — 로그인 상태 200, 미로그인 401.
- 단위 테스트: 실패 시 `isReady()` 거짓 + 사유 존재 + 화면 통보, 정지 후 사유 초기화, 미가동/재연결대기 중 중복 확인 안 함.

**미확인**: BiostarX 세션이 실제로 idle 만료될 때 장비가 소켓을 닫는지 여부(수 시간 관찰 필요). 다만 3분 주기 `verify()` 가 만료 자체를 예방하고, 만료돼도 탐지·복구하므로 어느 쪽이든 덮인다.
